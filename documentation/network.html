DocLynk Documentation

Network

DocLynk is built on top of a P2P Chord network. Reference the Chord Wikipedia Page .

Protocol

The data structures and tools for the network and used by node.h and node.cpp are located in proto.h. This file includes structs which hold information on a node. This is what is serialized into a binary stream by the cereal library to prevent unnecessary functions from being sent over the network. 

struct nInf {
        uint64_t id;
        std::string addr;
        std::string targetAddr;
        std::vector<RouteEntry> routeTable;
        std::vector<nInf> connections;

        template <class Archive>
        void serialize(Archive& ar) {
            ar(id, addr, targetAddr, routeTable, connections);
        }
    };

Proto.h also contains a struct used to hold only the needed values of another node in order to direct network traffic to it. This struct acts as an entry held in a node's routing finger table. 

struct RouteEntry {
        uint64_t startID;
        uint64_t nodeID;
        std::string addr;

        template <class Archive>
        void serialize(Archive& ar) {
            ar(startID, nodeID, addr);
        }
    };

In order for other nodes to process the data correctly, a Packet struct and a message type enum are used. The packet holds a nInf struct as a payload and stores other values for general routing. The message type is used in the node.h file to determine what is done with the packet. 

enum class MsgType : uint8_t {
        GetPredReq = 0,
        GetPredRes = 1,
        NotifyReq = 2,
        NotifyRes = 3,
        FindSuccReq = 6,
        FindSuccRes = 7,
        Ping = 4,
        Pong = 5
    };

    struct Packet {
        MsgType type;
        uint64_t packetID;
        uint64_t chordID;
        nInf payload;

        template <class Archive>
        void serialize(Archive& ar) {
            ar(type, packetID, chordID, payload);
        }
    };

The last two important networking features in proto.h are the functions to send and receive a packet. Both of these can be called with the file descriptor of a specified socket and the packet that should be sent as arguments. 

inline int sendPacket(int sockfd, Packet& packet) {
        std::stringstream ss;
        {
            cereal::BinaryOutputArchive archive(ss);
            archive(packet);
        }

        std::string payload = ss.str();

        uint32_t len = htonl(
            static_cast<uint32_t>(payload.size())
        );

        if (send(sockfd, &len, sizeof(len), 0) != sizeof(len))
            return -1;

        if (send(sockfd, payload.data(), payload.size(), 0)
            != (ssize_t)payload.size())
            return -2;

        return 0;
    }

    inline int recvPacket(int sockfd, Packet& packet) {
        uint32_t len;

        if (recv(sockfd, &len, sizeof(len), MSG_WAITALL) != sizeof(len))
            return -1;

        len = ntohl(len);

        std::string payload(len, '\0');

        if (recv(sockfd, payload.data(), len, MSG_WAITALL) != (ssize_t)len)
            return -2;

        std::stringstream ss(payload);

        cereal::BinaryInputArchive archive(ss);
        archive(packet);

        return 0;
    }

Node

Node.h contains all of the networking logic which is applied in node.cpp. The two main parts of this file are PeerConn, which is a class to easily represent the connection between two nodes, and a Node class which represents a device on the network.

PeerConn holds the addresses of the two nodes on the connection, the file descriptor of the socket, and contains the locks used to prevent race conditions when sending packets on the connection.

The Node class has a series of functions implementing Chord network P2P stabilizations and general network logic through a server and a client thread. You can reference Node.h to learn more specific information on how a node functions.

Node.cpp applies the code from Node.h by creating a node and acts as a starting point for the DocLynk daemon.
